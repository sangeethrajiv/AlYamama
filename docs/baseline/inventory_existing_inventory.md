# Inventory: existing implementation inventory

_Baseline of what exists in the codebase. Phase 1: no comparison with Odoo._

## 0. How to read this report

* **Source of truth:** the React/TypeScript code in `src/` (types in `src/types/accounting.ts`, `src/modules/*/types.ts`; screens in `src/components/` and `src/modules/`). Nothing was assumed from Odoo.
* **Backend:** there is **no backend and no database**. The app has no HTTP calls (`fetch`/`axios` do not appear in `src/`). All records live in React state (`useState` in `src/App.tsx`, `useContacts`, `useInventory`), seeded from mock data (`src/data/mockAccountingData.ts`, `src/data/mockInventory.ts`, `src/modules/*/data.ts`). Everything is lost on reload. Only the sign-in session (`src/auth/session.ts`) uses `localStorage` / `sessionStorage`.
  "Persisted" in this report therefore means **saved into in-memory state for the session**.
* **Technical Name:** `Model.field` is the TypeScript interface field; for table columns it is the field the column prints. `—` means the control is not bound to a model field (local component state or static text).
* **Data Type:** copied from the TypeScript interface (optional fields marked). For local-state controls the type is taken from the `useState` declaration.
* **Status definitions (as applied):**
  * **Implemented** – control exists, value is saved into state, and another screen or logic reads it (evidence in the Notes column: "read by ...").
  * **Partial** – control exists and saves, but nothing else reads it (stored only), or behaviour is limited / hard-coded / read-only.
  * **UI Only** – shown on screen but not bound to data (static text) or the stored value has no effect.
  * **Not Functional** – button/control with no real action (for example an `alert()` stub), or a model field with no UI and no logic in a flow that implies one.
* **"Read by"** comes from a scan for member access (`.field`) in every file other than the type/seed files. For the Accounting document forms (Invoice, Bill, Payment) the editing form files are ignored entirely, because they only read the value back to save it. For forms that share a file with their list or logic (Journal entries, Contacts, Inventory pages), form-binding lines (`useState`, `value=`, `onChange=`, `checked=`, `disabled=`, `placeholder=`) are ignored so only other logic that reads the value counts. It is an indicator, not a proof of correct behaviour. Fields with common names (`id`, `state`, `type`, `name`) will always appear used.
* Counts in this report are generated by script from the same table that is printed, so they match.

## 5. Existing functionality

### 5.1 Search, filters, grouping
Local search on each list; type/status/category filters; two Stock On Hand views (by product, by location+lot) act as the only grouping. No pagination, no column sorting.

### 5.2 Validation (checked on save/validate)
* Product: name and SKU required; SKU unique (case-insensitive), barcode unique, cost and price >= 0.
* Category: name required and unique; cannot delete a category that has products or children.
* Warehouse: name and short code required, code unique and without spaces or slashes. Location: unique name.
* Transfer: at least one line, product chosen, quantity > 0; internal source != destination; deliveries and internal transfers are blocked when stock at the source location is insufficient (per SKU; lot respected when given).
* Rule: product required, max >= min, one rule per product + warehouse.
* Adjustment: restricted by role; applies only changed counts.

### 5.3 Workflows (hook `src/modules/inventory/useInventory.ts`)
1. **Receipt / Delivery / Internal:** draft -> ready -> done (Validate) or cancel. Validate updates quants (`StockQuant` rows keyed by SKU + location + lot), appends `StockMove` rows, marks the transfer done. Services are skipped.
2. **Delivery from invoice:** pre-fills lines from invoice lines whose product matches a catalogue SKU or name.
3. **Adjustment:** counts -> `handleApplyAdjustment` (App) -> `applyCounts` updates quants, records moves, stores `InventoryAdjustment`, posts a Stock Journal entry and an audit log entry.
4. **Reordering:** `to order = ceil((max - onHand - incoming) / multiple) * multiple`; Order now / Order all create draft receipts grouped by preferred vendor.
5. **Integration with Accounting:** products populate invoice lines (SKU, description, price, unit, tax); invoice-line hover shows stock on hand; delivery can be created from a posted invoice. Posting an invoice does **not** create a delivery or reduce stock; receipts do **not** create vendor bills; stock valuation is only affected by adjustments.
6. **Integration with Contacts:** receipt vendor and delivery customer inputs suggest contacts by name.

### 5.4 Frontend / backend
No backend; quants are seeded from `src/data/mockInventory.ts` (12 quants) and products are derived from those quants (`seedProducts`) plus one service product. Company switcher filters quants only. All data is lost on reload.

## 8. Not present in the codebase

* Variants / attributes
* Units of Measure master (uom is a free-text field on Product and quants)
* Lots and Serial Numbers master (lot is a free-text field; tracking flag has no enforcement)
* Location master model (locations are strings)
* Packages / owners management (shown as read-only quant attributes)
* Valuation methods / landed costs
* Barcode scanning
* Multi-step routes
* Product images
