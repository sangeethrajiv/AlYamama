# Accounting: existing implementation inventory

_Baseline of what exists in the codebase. Phase 1: no comparison with Odoo._

## 0. How to read this report

* **Source of truth:** the React/TypeScript code in `src/` (types in `src/types/accounting.ts`, `src/modules/*/types.ts`; screens in `src/components/` and `src/modules/`). Nothing was assumed from Odoo.
* **Backend:** there is **no backend and no database**. The app has no HTTP calls (`fetch`/`axios` do not appear in `src/`). All records live in React state (`useState` in `src/App.tsx`, `useContacts`, `useInventory`), seeded from mock data (`src/data/mockAccountingData.ts`, `src/data/mockInventory.ts`, `src/modules/*/data.ts`). Everything is lost on reload. Only the sign-in session (`src/auth/session.ts`) uses `localStorage` / `sessionStorage`.
  "Persisted" in this report therefore means **saved into in-memory state for the session**.
* **Technical Name:** `Model.field` is the TypeScript interface field; for table columns it is the field the column prints. `—` means the control is not bound to a model field (local component state or static text).
* **Data Type:** copied from the TypeScript interface (optional fields marked). For local-state controls the type is taken from the `useState` declaration.
* **Status definitions (as applied):**
  * **Implemented** – control exists, value is saved into state, and another screen or logic reads it (evidence in the Notes column: "read by ...").
  * **Partial** – control exists and saves, but nothing else reads it (stored only), or behaviour is limited / hard-coded / read-only.
  * **UI Only** – shown on screen but not bound to data (static text) or the stored value has no effect.
  * **Not Functional** – button/control with no real action (for example an `alert()` stub), or a model field with no UI and no logic in a flow that implies one.
* **"Read by"** comes from a scan for member access (`.field`) in every file other than the type/seed files. For the Accounting document forms (Invoice, Bill, Payment) the editing form files are ignored entirely, because they only read the value back to save it. For forms that share a file with their list or logic (Journal entries, Contacts, Inventory pages), form-binding lines (`useState`, `value=`, `onChange=`, `checked=`, `disabled=`, `placeholder=`) are ignored so only other logic that reads the value counts. It is an indicator, not a proof of correct behaviour. Fields with common names (`id`, `state`, `type`, `name`) will always appear used.
* Counts in this report are generated by script from the same table that is printed, so they match.

## 5. Existing functionality

### 5.1 Search, filters, grouping, sorting
* **Search:** one global header box (Ctrl+K) feeding Invoices (number, partner, reference), Bills, Journal entries/items, Audit log and Contacts/Inventory lists.
* **Filters:** invoice type tabs; status segments on Invoices and Bills; payment partner type; CoA internal group; audit record type; report selectors.
* **Grouping:** none implemented anywhere (the group-by tags were removed). **Sorting:** none on Accounting lists (fixed insertion order, newest first).
* **Pagination:** none. **Export:** all export buttons are `alert()` stubs, except Print on Reports (`window.print`).

### 5.2 Workflows that exist (handlers in `src/App.tsx`)
1. **Invoice lifecycle:** `draft` -> Validate (`handleValidateInvoice`) -> `open` (residual = total; auto journal entry `<number>-JE`: debit receivable, credit revenue/VAT). Cash invoices also go to `open` and become `paid` only when a payment is registered. `in_payment` for partial payments, `paid` when residual is 0, `cancel` via `handleCancelInvoice` (blocked if already submitted to ZATCA).
2. **Credit note** (`handleCreateCreditNote`): methods draft / cancel (creates credit note and reconciles) / modify (also creates a new draft invoice). Credit notes are `Invoice` rows (`type: out_refund`).
3. **Proforma:** Save only; Renew (`handleRenewProforma`) creates a draft Credit invoice linked both ways; no payment or ZATCA on the proforma.
4. **Progressive:** single untaxed PO amount, Draft -> Approved; linked invoices shown in the card.
5. **ZATCA:** `handleSubmitZatca` **simulates** clearance (SHA-256 hash, UUID, chain index); there is no call to ZATCA.
6. **Payments** (`handleSavePayment`): creates `Payment`, updates invoice/bill residual and state, posts a journal entry, writes audit log.
7. **Reconciliation:** `handleReconcile` (one invoice + one payment, optional write-off), `handleBulkReconcile` (one payment to many invoices), `handleUnreconcile` (restores residual and state).
8. **Vendor bills:** approval status set on save (>=50,000 manager, >=200,000 director); `handleApproveBill` / `handleRejectBill` (reason, returns to draft); pay via PaymentModal.
9. **Journal entries:** create/save/post, must balance. `handleReverseJE` (creates a reversing entry) exists in `App.tsx` but **no UI control calls it**.
10. **Banking:** cheque Clear / Bounce (`handleClearCheque`, `handleBounceCheque`), direct bank charge/receipt (`handleRecordDirectBankTx`).
11. **Period close:** `handleAdvanceLockDate` updates hard/soft lock dates (Finance Director / Accounts Manager only).
12. **Audit & Chatter:** `addAuditLog` on every handler; `trackChanges` records field-level edits (`INVOICE_FIELDS`, `BILL_FIELDS`); `handlePostNote` for notes.
13. **Inventory adjustment accounting:** `handleApplyAdjustment` posts a Stock Journal entry and updates account balances.

### 5.3 Validations that exist
* Invoice: customer required and total > 0 (progressive: PO name, customer, PO total > 0), via `alert()`.
* Bill: vendor, supplier invoice number and total > 0; duplicate vendor + supplier-invoice-number warning banner.
* Payment: amount > 0 and partner required.
* Journal entry: debit must equal credit and be > 0.
* Bank transaction: amount > 0. Lock wizard: all 4 checkboxes ticked and role allowed.
* ZATCA: readiness checklist (customer name, 15-digit VAT, address, at least one line).
* Errors are shown mostly with the browser `alert()`; there is no inline field validation on the Accounting forms.

### 5.4 Role rules that exist
Validate button on the invoice list: Finance Director, Accounts Manager, Senior Accountant. Bill approval level 1: Finance Director, Accounts Manager; level 2: Finance Director. Lock-date advance: Finance Director, Accounts Manager. Inventory adjustments apply: Finance Director, Accounts Manager, Senior Accountant. Auditor is read-only in Contacts and Inventory only. The invoice/bill/payment/journal **forms are not role-gated**.

### 5.5 Frontend / backend integration
* **No backend.** All handlers mutate React state in `App.tsx`; mock seed data in `src/data/mockAccountingData.ts`.
* **Integration with other modules:** the customer / vendor inputs suggest names from Contacts and autofill VAT and invoice address; invoice line Product accepts catalogue SKUs from Inventory and fills description, price, unit and tax; new customers / vendors typed on invoices and bills are added to Contacts. Link is by **name string**, not by id.
* **Fields shown in the UI but not connected to anything downstream** are flagged Partial / UI Only in the table (for example Show Discount, Company Seal on Invoice, Show Out from Stock, Sales Team, Equipment Group Task, subscription fields, vehicles tab, thresholds tab, Journal select on journal entries).

### 5.6 Dead / legacy code
`src/components/EntryModal.tsx`, `Modal.tsx`, `StatCard.tsx`, `src/types.ts` and `src/data.ts` are an older, unused prototype (not imported by the app). `handleConvertToTaxInvoice` is still passed to the invoice list but the Convert button was removed.
