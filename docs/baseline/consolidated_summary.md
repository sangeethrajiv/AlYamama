# Consolidated baseline summary

_Phase 1 baseline of the three existing modules. Generated from the same data as the three inventory reports._

## 0. How to read this report

* **Source of truth:** the React/TypeScript code in `src/` (types in `src/types/accounting.ts`, `src/modules/*/types.ts`; screens in `src/components/` and `src/modules/`). Nothing was assumed from Odoo.
* **Backend:** there is **no backend and no database**. The app has no HTTP calls (`fetch`/`axios` do not appear in `src/`). All records live in React state (`useState` in `src/App.tsx`, `useContacts`, `useInventory`), seeded from mock data (`src/data/mockAccountingData.ts`, `src/data/mockInventory.ts`, `src/modules/*/data.ts`). Everything is lost on reload. Only the sign-in session (`src/auth/session.ts`) uses `localStorage` / `sessionStorage`.
  "Persisted" in this report therefore means **saved into in-memory state for the session**.
* **Technical Name:** `Model.field` is the TypeScript interface field; for table columns it is the field the column prints. `—` means the control is not bound to a model field (local component state or static text).
* **Data Type:** copied from the TypeScript interface (optional fields marked). For local-state controls the type is taken from the `useState` declaration.
* **Status definitions (as applied):**
  * **Implemented** – control exists, value is saved into state, and another screen or logic reads it (evidence in the Notes column: "read by ...").
  * **Partial** – control exists and saves, but nothing else reads it (stored only), or behaviour is limited / hard-coded / read-only.
  * **UI Only** – shown on screen but not bound to data (static text) or the stored value has no effect.
  * **Not Functional** – button/control with no real action (for example an `alert()` stub), or a model field with no UI and no logic in a flow that implies one.
* **"Read by"** comes from a scan for member access (`.field`) in every file other than the type/seed files. For the Accounting document forms (Invoice, Bill, Payment) the editing form files are ignored entirely, because they only read the value back to save it. For forms that share a file with their list or logic (Journal entries, Contacts, Inventory pages), form-binding lines (`useState`, `value=`, `onChange=`, `checked=`, `disabled=`, `placeholder=`) are ignored so only other logic that reads the value counts. It is an indicator, not a proof of correct behaviour. Fields with common names (`id`, `state`, `type`, `name`) will always appear used.
* Counts in this report are generated by script from the same table that is printed, so they match.

## 6. Missing backend connections

* There is **no backend, API, ORM or database** in the project (no `fetch`/`axios`, no server code). Every entity is an in-memory array initialised from mock data and reset on reload.
* Only the sign-in session is stored in the browser (`localStorage` or `sessionStorage`, key `ay.session`); authentication is checked locally against five demo accounts in `src/auth/users.ts`.
* No file storage: Contact photos / signature / seal are data URLs in memory; Bill attachments are a counter only; Invoice attachments have no control.
* ZATCA submission is simulated locally.
* Exports (Excel / CSV / XLSX) and CoA import are `alert()` stubs.
* Foreign keys do not exist: Invoice.partner, Bill.vendor, Payment.partner, Product.vendor, Transfer.partner are **name strings** matched against Contacts by exact text; Journal, Tax and Payment-terms are plain strings/values without master records.

## 7. Existing models and relationships

All models are TypeScript interfaces; there is no persistence layer.

```
Company ──(companyId)── Invoice / Bill / Payment / JournalEntry / Account / AnalyticAccount / ChequeRecord / StockQuant / InventoryAdjustment / FiscalPeriodConfig
Invoice 1─* InvoiceLine ;  Invoice 1─0..1 ZatcaSubmission ;  Invoice 0..1─0..1 Invoice (linkedInvoice, sourceProformaId, originInvoiceNumber)
Bill    1─* InvoiceLine (same line type)
Payment *─* Invoice / Bill          via matchedInvoiceIds[] and allocations[{invoiceId, amount}]
JournalEntry 1─* JournalLine ; JournalLine ──(accountId)── Account ; JournalLine ──(analyticAccountId)── AnalyticAccount
InvoiceLine ──(accountId / analyticAccountId)── Account / AnalyticAccount
ChequeRecord ──(relatedPaymentId, relatedInvoiceId)── Payment / Invoice
AuditLogEntry ──(recordType + recordId)── Invoice / Bill / Payment / JournalEntry / Chart of Accounts / Lock Date / Inventory Adjustment
Invoice.partner, Bill.vendor, Payment.partner  ····(name string)····  Contact
Contact 1─* ContactAddress ; Contact *─0..1 Contact (parentId: people and child companies)
Product *─1 ProductCategory (categoryId) ; ProductCategory *─0..1 ProductCategory (parentId)
Product ····(sku = StockQuant.productCode)···· StockQuant ; StockQuant.location = location name string
Transfer 1─* TransferLine ; TransferLine.sku ····Product.sku ; Transfer.from / to = location name strings
StockMove (log written by Transfer validation and adjustments) ; ReorderRule ── Product.sku + Warehouse.code
InventoryAdjustment 1─* InventoryAdjustmentLine ──(quantId)── StockQuant ; InventoryAdjustment ──(journalEntryNumber)── JournalEntry
Invoice line product ····Product.sku (autofill only, not stored as a relation)
```

Model files: `src/types/accounting.ts` (Accounting + StockQuant / InventoryAdjustment), `src/modules/contacts/types.ts`, `src/modules/inventory/types.ts`. Models that do **not** exist: Journal, Tax, PaymentTerm, UnitOfMeasure, Lot/Serial, StockLocation persistence (type exists only as a derived list), Variant, Customer/Vendor (Contact is used for both).
