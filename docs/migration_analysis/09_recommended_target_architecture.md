## 2. Frontend architecture
* **Nx monorepo**: `apps/shell`, `apps/users`, `apps/master-data`, `apps/accounting`, `apps/inventory`; `libs/{auth,permissions,company-context,api-client,ui-kit,i18n,money,audit-timeline,approval-widget,error-handling,link-resolver}`.
* **Native/Module Federation** with a runtime manifest; same Angular major everywhere; singletons pinned.
* Release train first, independent deploys later (doc 05).
* PDFs generated by the backend; Angular shows previews and triggers downloads.

## 3. Backend architecture
* Express + TypeScript; modules as in doc 06 §4; layering `controller → application service → domain → repository`.
* **Posting engine** (accounting) is the only writer of journal entries/items; inventory, invoices, payments, assets and vouchers call it through a port.
* **Sequence service** (gapless counters with row locks) shared by accounting, inventory, vouchers.
* **Policy service** (iam) translates the migrated record rules into scoped queries (doc 02 §3).
* **Approval service** parameterised by `(type, company, amount, date)` levels.
* **Job runner** for auto-reverse entries, asset depreciation, ZATCA submission/retry, stock notifications, auto-invoicing.
* **Report service**: SQL-based read models; async exports.

| `accounting` | accounting | accounts, journals, journal_sequences, taxes, tax_lines, invoices, invoice_lines, journal_entries, journal_items, payments, reconciliations (partial/full), analytic_accounts, vouchers, assets | `invoices` and `journal_entries` linked 1:1 like Odoo; `NUMERIC` money |
| `approvals` | approvals | approval_levels, approval_requests, approval_history | |
| `einvoicing` | einvoicing | documents, chain_state, credentials_ref | Keys only by reference to the secret manager |
| `audit` | platform | events, field_changes | Replaces chatter tracking |
| `platform` | platform | jobs, attachments_meta, config | |

Design principles: new clean schema with `legacy_odoo_id` + `legacy_model` on every migrated row; **money as `NUMERIC`**; explicit `company_id` everywhere; no soft-delete flag unless needed (use status); FKs and check/exclusion constraints; deferred constraint trigger for entry balance; no `ir_property`.

Alternative considered: **reuse the Odoo schema** and put Node on top of it. It speeds early read-only screens but inherits `ir_property`, the 110-column invoice table, and mixed concerns; reject for the long term, but acceptable for **read-only reporting** during the transition.

## 5. Authentication flow
1. User posts credentials to `/v1/auth/login` (TLS only; rate-limited; lockout; optional MFA for finance/admin).
2. Server verifies hash (PBKDF2-SHA512 import → re-hash to argon2id on success), creates a session record.
3. Response: short-lived access JWT (claims: `sub`, `sid`, `companyIds`, `activeCompanyId`, role ids — **not** the full permission list); refresh token in `HttpOnly; Secure; SameSite=Strict` cookie, rotating.
4. Shell keeps access token in memory; interceptor adds `Authorization` and `X-Company-Id`; silent refresh on 401.
5. Logout/revocation deletes the session; admin can revoke all sessions of a user.
6. Mobile: same endpoints with refresh token in secure storage; legacy `/api/authenticate` served by an adapter until retired.

## 6. Authorization flow
1. `authn` validates JWT and session.
2. `companyContext` checks `X-Company-Id ∈ user.companyIds` and sets the request's company scope.
3. `authz` checks permission `(resource, action)` from the cached role→permission set.
4. Repository applies the **policy scope** for `(user, resource, action, company)` — the translated `ir.rule` equivalents (ownership, HOD department, portal partner, state restrictions).
5. Domain service enforces state/approval guards (e.g., only an approver at the right level can approve; posted documents are immutable).
6. Every denial and every posting is written to the audit log.

## 7. Inter-module communication
* **Synchronous in-process calls** through module interfaces for commands that must be atomic (e.g., `inventory.validatePicking` → `accounting.postValuationEntry` inside one DB transaction).
* **Domain events** (in-process, transactional outbox table) for non-critical reactions (notifications, ZATCA submission queue, report cache invalidation).
* **Read models** for reporting only.
* If a module is later extracted, the in-process interface becomes an API/event contract without changing callers.

## 8. Centralised vs. independent

| Centralised (one implementation) | Independent per module |
|---|---|
| Authentication, session, authorization/policy engine, company context | Domain entities and use-cases |
| Audit log, error model, logging/tracing | Module REST routes and DTOs |
| Sequence service, money/decimal kernel, clock | Module-specific validators and state machines |
| Posting engine (ledger) | Module-specific screens (Angular remotes) |
| Approval engine | Module-specific reports |
| File/PDF/notification services, job runner | |
| Design system, API client, permission directives (frontend) | |
| Secret management | |

## 9. Transition architecture (important)
* During phased migration Odoo 12 stays system of record for modules not yet migrated. Define per phase: **who owns each table**, direction of sync, freeze windows, and a reconciliation report (doc 10).
* ZATCA: decide between **adapter to existing Odoo signer** vs **native implementation** *before* Milestone 6.
* Legacy `/api/*` consumers (mobile app) continue to work through a compatibility façade until they are updated.
